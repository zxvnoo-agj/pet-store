# Feature Specification: 小红书评论采集完善

**Feature Branch**: `008-xhs-review-improvement`  
**Created**: 2026-06-01  
**Status**: Draft  
**Input**: User description: "修改触发流程，当前是以SPU维度管理产品的，评论也是应当针对SPU的。在管理后台的SPU管理页，支持选择指定SPU后点击按钮触发评论采集。触发后，针对每一个SPU获取笔记、评论、链接、作者等信息保存，然后调用LLM针对评论提取出有用信息给出一个总结，保存。在小程序端，用户点击SPU的评价标签后，展示每条笔记以及下面的前十条评论，顶部展示AI总结。"

## Clarifications

### Session 2026-06-01

- Q: 现有每日凌晨3点的定时自动采集任务如何处理？ → A: 删除旧定时任务，改为纯手动触发（管理员在后台逐SPU操作）
- Q: 每次触发采集时最多采集多少条笔记？ → A: 20 条笔记（平衡质量和速度）
- Q: 采集过程中发生瞬时网络故障（非Cookie失效），已采集的部分如何处理？ → A: 保存已采集部分，标记为"部分成功"，后续可重新触发补全

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员触发SPU评论采集 (Priority: P1)

管理员在后台SPU管理页面，选择一个SPU后点击"评论采集"按钮，系统自动搜索小红书相关笔记，采集笔记正文、评论、作者、链接等数据，逐条调用LLM分析优缺点和推荐态度，保存到数据库。

**Why this priority**: 这是整个功能的数据来源。没有采集，后续的AI总结和前端展示都无法进行。

**Independent Test**: 管理员打开SPU管理页，选定一个SPU，点击"评论采集"按钮，等待完成后在数据库`reviews`表中能看到新增的评论记录，且每条记录包含`tags`（优缺点标签）、`is_recommended`（推荐态度）、`llm_review_result`（LLM分析结果），source_url 字段包含小红书原始链接。

**Acceptance Scenarios**:

1. **Given** SPU管理页面中展示SPU列表，**When** 管理员选择一个SPU并点击"评论采集"按钮，**Then** 系统开始采集过程，显示"采集中…"状态，采集完成后显示"已采集 N 条评论"。
2. **Given** 该SPU已有部分评论数据，**When** 再次触发采集，**Then** 系统跳过已存在的笔记（按笔记唯一标识去重），只新增未采集过的笔记。
3. **Given** 小红书搜索该SPU关键词无结果，**When** 采集任务执行，**Then** 系统记录"无搜索结果"状态并通知管理员。
4. **Given** 采集过程中小红书Cookie失效，**When** API返回认证错误，**Then** 系统停止采集并提示管理员"Cookie已失效，请更新后重试"。
5. **Given** 同一个SPU已有进行中的采集任务，**When** 管理员再次点击采集按钮，**Then** 系统提示"该SPU已有进行中的采集任务，请稍后再试"。
6. **Given** 采集过程中发生瞬时网络故障（非Cookie问题），**When** 部分笔记采集成功但部分失败，**Then** 系统保存已成功的笔记，任务状态显示"部分成功：已采集 N 条"，后续管理员可重新触发补全。

---

### User Story 2 - LLM生成SPU评价总结 (Priority: P2)

采集完成后，系统调用LLM对该SPU所有已采集的小红书评论进行聚合分析，生成一份结构化总结（整体优缺点、推荐率、使用体验总结），保存到SPU记录中。

**Why this priority**: AI总结是小程序端展示价值的核心内容，但依赖于P1的采集数据。可以在有数据后再触发生成。

**Independent Test**: 当SPU有已采集的评论后，触发总结生成，检查该SPU记录的`ai_review_summary`字段是否包含结构化的总结内容（整体优缺点、推荐率、一句话总结）。

**Acceptance Scenarios**:

1. **Given** SPU已有至少3条已采集评论，**When** 采集任务完成时自动触发总结生成，**Then** LLM分析所有评论并保存到SPU的AI总结字段，内容包括：整体优点、整体缺点、综合推荐结论、一句话总结。
2. **Given** SPU评论数不足3条或全部为中性，**When** 触发总结生成，**Then** 系统记录"评论数不足，无法生成有参考价值的总结"。
3. **Given** LLM API调用失败，**When** 总结生成出错，**Then** 系统记录错误日志，SPU的AI总结字段标记为空，不影响评论数据正常展示。
4. **Given** 该SPU已经有一份AI总结，**When** 新增采集完成后重新生成，**Then** 新总结基于全部评论（包括新旧）重新聚合，覆盖旧总结。

---

### User Story 3 - 小程序端展示评论与AI总结 (Priority: P3)

用户在小程序端浏览SPU详情页，点击"评价"标签后，进入评价详情页。页面顶部展示AI总结（整体优缺点、推荐率），下方逐条展示采集的小红书笔记（正文、作者、点赞数、发布时间、来源链接），每条笔记下方折叠展示前10条评论。

**Why this priority**: 这是最终对用户交付的价值。依赖P1数据采集和P2总结生成，但可以用预置数据独立开发前端界面。

**Independent Test**: 为测试SPU预置几条评论数据和AI总结，在小程序中打开该SPU的评价页，验证AI总结展示区域、笔记列表、每条笔记的评论展开折叠功能均正常。

**Acceptance Scenarios**:

1. **Given** SPU有AI总结和已采集评论，**When** 用户点击SPU详情页的"评价"标签，**Then** 进入评价详情页，顶部显示"AI分析总结"区域，包含整体优缺点标签和一句话总结。
2. **Given** 评价详情页已展示，**When** 用户滚动浏览，**Then** 看到每条小红书笔记卡片，包含：正文摘要（超过200字时折叠）、作者昵称、点赞数、发布时间、查看原文链接。
3. **Given** 某条笔记有评论数据，**When** 用户点击"查看评论"，**Then** 展开显示前10条评论内容，再次点击折叠。
4. **Given** SPU暂无AI总结（评论数不足），**When** 用户进入评价页，**Then** 顶部不显示AI总结区域，直接展示零散的笔记卡片。
5. **Given** SPU有采集的笔记但暂时只有1-2条，**When** 用户进入评价页，**Then** 展示所有可用笔记，AI总结区域显示"评论较少，待更多数据后生成总结"。

---

### Edge Cases

- 小红书笔记内容过长（超过2000字）时如何处理截断？
- 评论数超过10条时如何分页或折叠？
- 笔记作者的昵称包含特殊字符或emoji时是否正确显示？
- 笔记中包含图片时，小程序端是否展示缩略图？
- 多条笔记来自同一个作者时是否标记？
- 采集结果超过20条笔记时前端如何加载（分页/无限滚动）？
- 用户在评价页期间有新评论入库，是否需要刷新机制？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 管理后台SPU管理页 MUST 为每个SPU提供"评论采集"操作按钮
- **FR-002**: 系统 MUST 以SPU的品牌+名称为关键词搜索小红书笔记
- **FR-003**: 系统 MUST 采集每条笔记的：正文内容、前10条评论、作者昵称、点赞数、发布时间、小红书原文链接
- **FR-004**: 系统 MUST 将采集的评论关联到对应SPU，按笔记唯一标识去重，不重复采集同一篇笔记
- **FR-005**: 系统 MUST 对每条采集的笔记调用LLM分析，提取优缺点标签和推荐态度
- **FR-006**: 系统 MUST 在采集完成后自动调用LLM生成该SPU的聚合AI总结
- **FR-007**: 采集任务 MUST 有状态跟踪（待处理/进行中/已完成/部分成功/失败），管理员可见
- **FR-008**: 小程序端评价详情页 MUST 顶部展示AI总结区域（整体优缺点、推荐率、一句话总结）
- **FR-009**: 小程序端 MUST 以笔记卡片形式展示每条采集的小红书笔记，含正文、作者、点赞数、发布时间
- **FR-010**: 小程序端每条笔记 MUST 支持折叠/展开查看前10条评论
- **FR-011**: 系统 MUST 在采集过程中遵守请求间隔限制（≥2秒），避免被平台封禁
- **FR-012**: 系统 MUST 在Cookie失效时终止采集并提示错误信息
- **FR-013**: 系统 MUST 在搜索无结果时记录"无结果"状态
- **FR-014**: 同一SPU同一时刻 MUST 只允许一个采集任务运行（防重复触发）
- **FR-015**: 系统 MUST 移除旧的每日定时自动采集任务（daily_review_fetch），评论采集改为仅由管理员手动触发
- **FR-016**: 每次触发采集 MUST 最多采集20条小红书笔记，超出部分忽略
- **FR-017**: 采集过程中发生非认证类错误（瞬时网络故障等），系统 MUST 保留已采集部分、标记"部分成功"，不可因部分失败而回滚全部数据

### Key Entities

- **Review（评价记录）**: 已有实体。存储单条小红书笔记的采集结果，关联到SPU。包含笔记正文、评论列表、作者、点赞数、发布时间、来源URL、LLM单条分析结果（优缺点标签、推荐态度）。
- **SPU**: 已有实体。新增 `ai_review_summary` 字段，存储LLM聚合分析后的综合总结（整体优缺点、推荐率、一句话总结）。
- **Collection Job（采集任务）**: 跟踪单次采集操作的进度和结果，包含状态、采集数量、错误信息。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可在3次点击内完成触发一个SPU的评论采集
- **SC-002**: SPU有10条以上小红书笔记时，采集全流程（搜索→采集→LLM分析）在2分钟内完成
- **SC-003**: 采集完成后60秒内AI总结生成完毕
- **SC-004**: 小程序端评价页在有数据的情况下，2秒内完成渲染
- **SC-005**: 非小红书平台原因的采集失败率低于5%
- **SC-006**: 重复采集的笔记100%被去重过滤，不产生重复记录

## Assumptions

- 小红书API端点保持当前结构不变，继续使用Cookie认证方式
- 已有LLM服务（DashScope）可复用于单条分析和聚合总结
- 管理后台已有SPU管理页面，可直接添加采集按钮
- 小程序SPU详情页已有评价入口，可扩展为完整的评价详情页
- 现有XHSCollector的Cookie管理和限流机制可直接复用
- SPU的brand和name字段已有数据（采集依赖这些字段生成搜索关键词）
- 笔记中的图片暂不展示（仅采集和展示文字内容），后续版本再支持
