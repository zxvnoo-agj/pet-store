# Feature Specification: 自建用户评价功能

**Feature Branch**: `009-in-app-reviews`  
**Created**: 2026-06-13  
**Status**: Draft  
**Input**: User description: "自建评论功能，要求：小程序端引导真实用户提交'使用体验/踩坑/推荐理由'，逐步形成自己的评价池。小红书内容适合作为冷启动素材，但长期最好不要依赖外部平台评论。你们现在已经有 reviews 表和 AI 总结能力，可以把来源拆成：user：小程序用户评价、xhs_manual：人工导入小红书内容、xhs_auto：自动采集成功时的数据、admin_seed：运营整理内容。前端展示时可以统一进'真实评价'，但标注来源即可。"

## Clarifications

### Session 2026-06-13

- Q: FR-014 用户提交评价后在列表中立即看到的内容 vs 审核中状态？ → A: 显示"审核中"占位卡片，仅提交者本人可见，标注审核状态，对其他用户不可见
- Q: 评价列表默认排序方式？ → A: 最新优先（按创建时间倒序）
- Q: 评价被拒绝后是否通知用户？ → A: 本次版本不做通知，管理员拒绝时填写原因仅存档备查
- Q: 敏感词检测方案？ → A: 自建简易敏感词库（本地中文词表），后端进行关键词匹配检测
- Q: 评价内容超过2000字如何处理？ → A: 最大500字限制，前端+后端双重校验，鼓励简洁评价

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 小程序用户提交评价 (Priority: P1)

普通用户在小程序端浏览SPU详情时，可进入评价页面查看已有评价，并提交自己的使用体验评价，包括评分、心得体会（亮点/缺点/推荐理由）、标记是否推荐。本次版本仅支持文字评价，不支持图片。

**Why this priority**: 这是自建评价功能的核心入口。没有用户评价提交，就无法形成自有评价数据积累，后续的展示和运营都无从谈起。

**Independent Test**: 一个小程序用户打开任一SPU评价页，点击"写评价"按钮，填写评分（1-5星）、输入使用体验文字、勾选"推荐"开关后提交；提交成功后可在评价列表中看到自己刚提交的评价。

**Acceptance Scenarios**:

1. **Given** 用户已登录并浏览SPU详情页，**When** 点击"评价"标签进入评价页并点击"写评价"，**Then** 打开评价表单：星级评分（必填）、体验描述文本框（必填，引导提示"分享你的使用体验、踩过的坑或推荐理由"）、是否推荐开关（可选），提交按钮。
2. **Given** 用户填写完毕并提交，**When** 表单数据合法，**Then** 评价保存成功，该条评价标记来源为"user"，返回评价列表页，提交者本人可见"审核中"占位卡片（标注"等待审核"），其他用户不可见该评价。
3. **Given** 用户未填写必填项（评分或内容为空），**When** 点击提交，**Then** 提示"请完成必填项"，不提交数据。
4. **Given** 用户未登录，**When** 点击"写评价"按钮，**Then** 引导用户先完成登录，登录后返回评价表单页。
5. **Given** 用户已对该SPU提交过评价，**When** 再次打开评价表单，**Then** 提示"你已评价过该产品"，不可重复提交。
6. **Given** 用户提交评价内容包含敏感词，**When** 系统检测到敏感内容，**Then** 提示"内容包含不当信息，请修改后重新提交"。

---

### User Story 2 - 评价来源拆分与标注 (Priority: P1)

系统对评价按来源分类管理：小程序用户评价（user）、人工导入小红书内容（xhs_manual）、自动采集小红书数据（xhs_auto）、运营整理内容（admin_seed）。前端展示时统一进入"真实评价"列表，每条评价标注其来源标签。

**Why this priority**: 来源拆分是用户明确要求的核心设计，影响数据模型和前端展示。没有这个拆分，自建评价和外部导入的评价无法区分，影响用户信任度和运营策略。

**Independent Test**: 在管理后台创建一条来源为"admin_seed"的评价，在小程序端打开该SPU的评价页，验证该评价出现在"真实评价"列表中且带有"运营整理"来源标注。

**Acceptance Scenarios**:

1. **Given** 一个SPU同时存在4种来源的评价，**When** 用户在小程序打开该SPU的评价页，**Then** 所有已审核通过的评价统一展示在"真实评价"列表中，每条评价卡片标注来源（"用户评价"/"小红书" /"运营整理"）。
2. **Given** 管理后台查看评价列表，**When** 管理员打开评价管理页，**Then** 每条评价显示来源标签，可按来源类型筛选。
3. **Given** 自动采集任务成功采集小红书笔记，**When** 笔记保存为评价记录，**Then** 其来源自动标记为"xhs_auto"。
4. **Given** 管理员通过后台手动导入小红书内容，**When** 内容保存为评价记录，**Then** 其来源标记为"xhs_manual"。
5. **Given** 小程序用户通过P1流程提交评价，**When** 评价保存，**Then** 其来源自动标记为"user"。

### User Story 3 - 小程序端评价展示（统一"真实评价"） (Priority: P2)

小程序端的评价详情页将所有来源的评价统一展示为"真实评价"列表，顶部保留AI总结（如可用），每条评价展示评分、内容、来源标签、是否为推荐评价，支持分页加载。

**Why this priority**: 评价展示直接面向终端用户，是自建评价价值的最终交付。依赖P1的用户评价提交和来源拆分，但展示UI可先基于现有数据独立开发。

**Independent Test**: 预置不同来源（user/xhs_auto/admin_seed）的评价数据，在小程序中进入评价页，验证所有评价统一展示且来源标注正确，分页加载正常。

**Acceptance Scenarios**:

1. **Given** SPU有至少一条评价（任意来源），**When** 用户进入评价页，**Then** 页面顶部展示AI总结（如可用），下方展示评价列表，每条评价卡片包含：评分星级、评价正文、来源标签、是否推荐标识、发布时间。
2. **Given** SPU评价总数超过20条，**When** 用户滚动到列表底部，**Then** 自动加载下一页评价（分页加载）。
3. **Given** 某SPU暂无任何评价，**When** 用户进入评价页，**Then** 显示空状态提示"暂无评价，来写第一条评价吧"，并引导用户提交。
4. **Given** 用户查看一条来自小程序的用户评价，**When** 观察来源标签，**Then** 显示"用户评价"标签（与"小红书""运营整理"标签视觉区分）。

### User Story 4 - 管理后台评价管理（来源筛选与审核） (Priority: P2)

管理员在后台可查看所有评价（按来源筛选、按状态筛选），审核用户提交的评价（通过/拒绝），手动添加运营整理的评价内容。

**Why this priority**: 评价质量管理是保证"真实评价"可信度的关键。审核能力防止垃圾评价上线，手动添加能力支持运营冷启动。

**Independent Test**: 管理员在后台评价管理页，筛选来源为"user"且状态为"pending"的评价，对一条评价点击"通过"，验证该评价在前端可见。

**Acceptance Scenarios**:

1. **Given** 管理员打开评价管理页，**When** 查看评价列表，**Then** 每条评价展示：来源标签、状态、SPU名称、评分、内容摘要、提交时间；支持按来源（user/xhs_manual/xhs_auto/admin_seed）和状态（pending/approved/rejected）筛选。
2. **Given** 一条用户提交的评价状态为"pending"，**When** 管理员点击"通过"，**Then** 该评价状态变为"approved"，小程序端可见；管理员点击"拒绝"，则状态变为"rejected"，小程序端不可见。
3. **Given** 管理员需手动添加运营整理的评价，**When** 点击"添加评价"并选择目标SPU，填写评价内容、评分、来源选择"admin_seed"，**Then** 评价直接以"approved"状态入库，标注来源"运营整理"。

---

### User Story 5 - AI总结兼容多来源评价 (Priority: P3)

LLM生成SPU评价总结时，综合所有来源（不仅限于小红书）的已审核评价进行分析，生成更全面的AI总结。管理员可在后台手动触发重新生成总结。

**Why this priority**: AI总结是评价页的关键展示内容。扩展到多来源数据能提升总结质量，但依赖P1和P2的数据积累，可在有足够评价数据后再优化。

**Independent Test**: 为一个SPU预置不同来源的评价（user + xhs_auto + admin_seed），触发AI总结生成，验证总结内容涵盖所有来源的评价信息。

**Acceptance Scenarios**:

1. **Given** SPU拥有多来源（user/xhs/xhs_manual/admin_seed）且已审核的评价，**When** 触发AI总结生成，**Then** LLM综合所有来源的评价进行分析，生成的总结覆盖所有来源的有效评价内容。
2. **Given** SPU仅有单一来源的评价（如仅有xhs_auto），**When** AI总结生成，**Then** 正常生成总结（不因来源单一而异常）。
3. **Given** 管理员认为当前AI总结不够新，**When** 在后台SPU管理页点击"重新生成总结"，**Then** 系统基于当前所有已审核评价重新调用LLM生成并更新总结。

---

### Edge Cases

- 评价内容最大500字，超过时前端限制输入且后端校验拒绝
- 同一用户对同一SPU重复评价（通过不同入口）时如何防止？
- 评价被拒绝后本次版本不主动通知用户，管理员拒绝时填写原因存档备查
- 用户提交评价时网络中断，已填写的内容是否保留（草稿机制）？
- 运营手动添加评价时，评分、内容等字段的校验规则是否与用户提交一致？
- 评价列表默认按最新优先排序（创建时间倒序）
- 用户是否可以编辑或删除自己已提交的评价？
- 历史评价数据（source字段为"user"但实际可能来自旧逻辑）如何处理迁移？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持小程序用户提交评价，包括评分（1-5星）、文字内容、是否推荐标记（可选）。本次版本不支持图片上传。
- **FR-002**: 系统 MUST 对用户评价进行必填项校验（评分和内容为必填）
- **FR-003**: 系统 MUST 限制同一用户对同一SPU只能提交一条评价
- **FR-004**: 系统 MUST 对用户评价内容进行敏感词检测，拒绝包含敏感内容的评价
- **FR-005**: 系统 MUST 将评价来源（source 字段）正式拆分为四种类型：
  - `user`：小程序用户提交的评价
  - `xhs_manual`：管理员手动导入的小红书内容
  - `xhs_auto`：自动采集任务成功时保存的小红书数据
  - `admin_seed`：管理员在后台手动添加的运营内容
- **FR-006**: 采集任务保存评论时 MUST 自动标记 source 为 `xhs_auto`（而非原默认值）
- **FR-007**: 小程序端评价展示页 MUST 将所有已审核评价统一展示为"真实评价"列表
- **FR-008**: 每条评价在前端展示时 MUST 标注其来源（用户评价 / 小红书 / 运营整理），不同来源在视觉上有区分
- **FR-009**: 管理员在后台 MUST 可按来源类型（user/xhs_manual/xhs_auto/admin_seed）和状态（pending/approved/rejected）筛选评价列表
- **FR-010**: 管理员 MUST 可审核用户提交的评价（通过/拒绝），审核通过后评价在小程序端可见
- **FR-011**: 管理员 MUST 可在后台手动添加运营整理的评价（source=admin_seed），直接以 approved 状态入库
- **FR-012**: AI总结生成 MUST 综合所有来源的已审核评价进行分析，不局限于单一来源
- **FR-013**: 未登录用户点击"写评价"时 MUST 被引导至登录流程，登录后返回评价表单
- **FR-014**: 用户提交评价后 MUST 在评价列表中看到自己的评价以"审核中"占位卡片展示（仅自己可见），标注"等待审核"状态；其他用户不可见该评价
- **FR-015**: 小程序端评价列表 MUST 默认按创建时间倒序排列（最新评价在前）
- **FR-016**: 管理员拒绝评价时 MUST 填写拒绝原因，原因存档备查（本次版本不做用户端通知）
- **FR-017**: 评价文字内容 MUST 限制最大500字，前端输入框限制 + 后端校验双重保障

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从小程序SPU详情页进入评价页并完成写评价流程，整个流程在2分钟内完成（含登录步骤）
- **SC-002**: 用户提交评价后，审核通过的评价在30秒内出现在小程序评价列表中
- **SC-003**: 管理员可在10秒内完成一条来自任何来源的评价的审核操作（通过/拒绝）
- **SC-004**: 小程序评价页在评价列表含50条评论时，首次加载在2秒内完成
- **SC-005**: 评价来源标签的识别准确率100%（所有来源标注与数据库实际来源一致）
- **SC-006**: 上线后3个月内，小程序用户自建评价数量占该SPU总评价（不含审核未通过）的比例达到30%以上
- **SC-007**: 90%的用户在提交评价时能一次成功完成（不被表单校验错误或系统错误中断）

## Key Entities

- **Review（评价记录）**: 已有实体。新增明确的来源枚举约束（user/xhs_manual/xhs_auto/admin_seed）。关联 SPU 和可选的 User（仅 user 来源时有 user_id）。包含评分、文字内容、标签、推荐标记、来源标签、来源URL（仅外部来源）、审核状态。本次版本不支持图片。
- **SPU**: 已有实体。AI总结字段扩展为综合所有来源评价，不再仅限小红书数据。
- **User（小程序用户）**: 已有实体。用户评价提交关联用户ID，用于限制同一用户同SPU重复评价。

## Assumptions

- 现有 reviews 表的 `source` 字段已支持字符类型，可直接存储四种来源值
- 现有用户登录体系（微信授权登录）可复用，评价提交需登录态
- 管理后台已有评价管理页面（admin_reviews 路由），可在此基础上扩展
- 小程序端已有SPU详情页和评价入口（008特性成果），可在此基础上扩展
- 敏感词检测采用自建简易中文词库，后端进行关键词匹配，不依赖外部审核 API
- 图片上传暂不在本次版本支持，评价仅限文字内容
- 历史评价数据中 source 为 "user" 但实际为旧自动采集数据的，可作为已知数据迁移问题在后继执行阶段处理
- 用户评价提交后默认进入"pending"状态，需要 admin 审核通过后才在前端可见；admin_seed 来源的评价默认 approved
